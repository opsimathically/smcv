# Native local-lab HTTPS

Status: **Native local-lab HTTPS procedure**
Last tested: 2026-07-22

## What this listener is

SMCV can expose the product UI and `/api/v1` on a second native HTTPS listener.
It is opt-in. The existing `SMCV_LISTEN_ADDR` listener remains plaintext and
loopback-only for ForwardDynamic, nginx, or another same-host proxy. Metrics
remain on their separate loopback-only address.

Native lab HTTPS is intended for a trusted local network, not unrestricted
Internet exposure. Scope the host firewall and systemd network policy to the
intended management subnet.

## Quick start with a generated self-signed certificate

Choose the exact DNS name you will enter in the browser and an explicit local
interface address:

```text
SMCV_LAB_HTTPS_ADDR=192.168.50.10:8443
SMCV_LAB_HTTPS_SERVER_NAME=vault.lab.example
```

The name must resolve to the bind address from each intended client. Do not use
`0.0.0.0` or `::`; SMCV accepts only an explicit loopback, private/unique-local,
or link-local address and rejects zero-port, unspecified, multicast, or
globally routable binds. Keep `SMCV_LISTEN_ADDR` on loopback.

When neither supplied-certificate setting exists, preflight creates:

```text
${SMCV_KEY_DIR}/lab-https-cert.pem
${SMCV_KEY_DIR}/lab-https-key.pem
```

Both files are owner-only mode 0600. The leaf is non-CA, valid for 365 days,
has server-auth usage, and contains the configured DNS name or IP as an exact
subject alternative name. Preflight prints the direct HTTPS origin, SHA-256
leaf fingerprint, and certificate expiry as a Unix timestamp.

Run preflight under the exact service identity and environment:

```text
smcv-server preflight
```

Compare the printed fingerprint over a separate trusted channel before
accepting or installing the certificate on a client. One independent check is:

```text
openssl x509 -in /var/lib/smcv-key/lab-https-cert.pem \
  -noout -fingerprint -sha256
```

A browser warning bypass provides encryption but does not prove that the
browser reached the intended server. Prefer importing the verified certificate
into a dedicated lab browser/OS trust store. Trust-store steps are
browser/operating-system specific; remove the trust entry when the lab is
retired or the certificate is replaced.

SMCV reuses the same generated bytes on every restart. It does not silently
renew, regenerate, overwrite, or repair them. Back up the certificate if useful
for client comparison, but protect the private key with the same host custody
as other key-provider material. If either generated file is missing, corrupt,
expired, unsafe, or no longer matches the configured name, preflight fails and
requires an explicit operator decision.

## Use a local or public CA certificate

Place a leaf-first PEM chain and its matching PEM private key in protected
absolute paths readable by the SMCV service identity. The files must be regular
non-symlinks, owned by that identity, non-empty, bounded, and mode 0600:

```text
SMCV_LAB_HTTPS_CERT_FILE=/var/lib/smcv-key/lab-https-chain.pem
SMCV_LAB_HTTPS_KEY_FILE=/var/lib/smcv-key/lab-https-key.pem
```

Set both or neither. SMCV validates current time validity, an exact configured
DNS/IP SAN, and certificate/private-key compatibility before readiness. It
does not obtain, issue, renew, or hot-reload certificates. To replace or renew,
stage and verify the new pair with restrictive custody, update both paths (or
replace both while the service is stopped), run preflight, then restart.

Retain the generated pair until the CA pair has passed preflight and a client
test. Remove obsolete private keys through the operator's protected deletion
procedure; do not commit them or include them in support bundles.

## Canonical origin and passkeys

SMCV has one canonical browser origin and one WebAuthn RP per process:

- In a no-proxy trial using a DNS lab name, omit `SMCV_ORIGIN` and
  `SMCV_RP_ID`; SMCV derives them from the native HTTPS name and port.
- For an IP-address lab URL, or when the proxy remains canonical, configure a
  valid explicit origin/RP relationship. Password workflows can use the direct
  HTTPS route, but SMCV does not promise that passkeys bound to another
  origin/RP will work there.
- A self-signed certificate normally must be installed as trusted before a
  browser exposes WebAuthn/passkey functionality.

Changing canonical origin or RP can strand existing passkey credentials.
Confirm password recovery access and follow the authenticator reenrollment
procedure before making that change.

## Systemd and firewall

The packaged service deliberately denies non-loopback network traffic by
default. Add a local systemd drop-in that permits only the actual management
subnet; do not edit the packaged unit:

```text
# /etc/systemd/system/smcv.service.d/lab-https.conf
[Service]
IPAddressAllow=192.168.50.0/24
```

Run `systemctl daemon-reload`, re-run preflight as the service identity, and
restart. Configure the host firewall equivalently for the one TLS port and
source subnet. Never expose the metrics port or loopback HTTP port.

To disable native HTTPS, remove all four `SMCV_LAB_HTTPS_*` settings and the
systemd/firewall allowance, then restart. Retain or deliberately retire the
certificate files according to your custody policy; SMCV does not delete them.

## Verification

From a client that trusts the intended certificate or CA:

```text
curl --cacert verified-ca-or-leaf.pem \
  https://vault.lab.example:8443/health/ready
```

Confirm that plaintext sent to the TLS port fails, the loopback proxy path
still works, and metrics remain reachable only on the host. The repository
campaign `./scripts/lab-https-smoke.sh` performs generated/certified modes,
restart stability, plaintext rejection, and negative custody/key tests entirely
under a temporary directory and removes it on exit.
